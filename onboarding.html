1. What is demand forecasting?

Demand forecasting means predicting how many units of a product will sell (here: ship) in future time periods, using historical sales patterns plus anything else that plausibly drives demand — day of week, season, holidays, weather, price, promotions. A forecast is only useful if you can also measure how wrong it is, which is why this whole project is organized around one metric: WAPE (Weighted Absolute Percentage Error) — see the glossary for the formula. Lower WAPE = more accurate forecast.

Two things make this problem harder than "fit a line through history":

  • Intermittency — many (product, location) combinations sell 0 units on most days and a handful of units on others. A model that's great at forecasting a steadily-selling product can do badly here.
  • Multi-step / recursive forecasting — to predict 28 days ahead, the model's day-8 prediction depends on features built from its own day-1..7 predictions (since the real actuals for those days don't exist yet). Errors can compound the further out you forecast.

2. What we're trying to do

Forecast shipped_units at the ASIN × postal_code × day grain for a Japanese bottled-water business — i.e. for each product (ASIN) and each delivery postal code, how many units ship on each future day.

Scope20 ASINs × 19 postal codes → 217 active series (product/location pairs with any sales history)
History2023-01-01 → 2025-12-31, 312,705 shipment-level rows, 771,510 total units
Backtest designTrain on 2023–2024, test on all of 2025 (a genuine out-of-sample holdout)
Series shapeMixed: Syntetos–Boylan classification found 66 smooth, 52 erratic, 54 lumpy, 45 intermittent series
Known signallag-1 autocorrelation 0.78, lag-7 0.63 (weekly cycle), summer demand peak, ~25%/yr upward trend

We report WAPE at three aggregation levels (overall daily total, per-SKU, and the native SKU×ZIP grain — error naturally shrinks as you aggregate, so all three numbers matter) and specifically segment peak vs non-peak demand, because that split is where most of the current forecasting error hides. More in Current results.

3. How the pipeline works

Everything happens in forecast.py, in six stages:

  1. Load & aggregate — read the shipment-level TSV, sum to one row per (ASIN, postal_code, day).
  2. Densify — reindex every series onto a full daily calendar from its first sale onward, zero-filling no-ship days. Without this, lag/rolling features would be calendar-wrong for intermittent series.
  3. Feature engineering — lags (1..28 days, plus 364/365/371-day "same time last year" lags), rolling mean/std/max/active-rate over 7/14/28-day windows, calendar features, Japanese holidays (via jpholiday), price/discount, weather, and hand-built "peak anticipation" interaction features (promo × weekend, promo × heat, etc.).
  4. Train — a single global LightGBM regressor (one model across all 217 series, not one model per series) with a Tweedie loss, which natively handles non-negative, zero-inflated counts.
  5. Backtest — forecast the holdout period recursively (each day's prediction feeds the next day's lag features) and score against two baselines: same-day-last-year, and Croston/TSB (a classic intermittent-demand method).
  6. Forward forecast (optional) — refit on all available data and roll forward beyond the end of history.
Why one global model instead of one per series? With 217 series, many of them sparse, a global model shares statistical strength across series (a lumpy series still benefits from what the model learned about seasonality/holidays from the dense ones) — this was an explicit design decision, not an oversight.

5. Setup

Get the raw data

With_Price.tsv is not committed to this repo — it's real shipment/pricing/discount data and this repo is public on GitHub, so it's kept out deliberately. Ask whoever onboarded you for the file (columns: ship_day, asin, warehouse_id, subcategory_code, subcategory_description, postal_code, zipcode_category, shipped_units, avg_our_price, avg_discount_amt) and place it wherever you like — you'll pass its path via --input.

Python environment

cd forecast
python3 -m venv .venv
.venv/bin/pip install -e .   # or: pip install numpy pandas lightgbm jpholiday certifi
macOS only: LightGBM needs the OpenMP runtime, which isn't part of the OS. If you hit Library not loaded: @rpath/libomp.dylib, run: 
brew install libomp

6. Running / testing commands

Run the current best-known backtest

.venv/bin/python forecast.py \
  --input /path/to/With_Price.tsv \
  --train-end 2024-12-31 \
  --refresh-days 28 \
  --known-prices \
  --weather weather.tsv \
  --calibrate

This trains on ≤2024-12-31 and does a rolling-origin backtest over all of 2025 (re-seeds lag features with real actuals every 28 days instead of one single-shot 365-day recursive run — see glossary for why that matters). It writes backtest_2025.tsv + backtest_2025.meta.json and prints a metric table. Sanity check: you should land close to daily WAPE ≈ 0.49, monthly WAPE ≈ 0.16, volume error within a couple points of 0% — if you're wildly off, something's different about your input data or environment.

Then look at the breakdown

.venv/bin/python peak_wape.py            # console: peak vs non-peak vs zero-demand
.venv/bin/python wape_levels.py          # console: WAPE at 3 aggregation grains
.venv/bin/python generate_report.py      # writes wape_report.html (open it in a browser)

All three default to reading backtest_2025.tsv from the repo root, so just run them after the backtest above with no arguments.

Other useful flags on forecast.py

FlagWhat it does
--refresh-days NRolling-origin cadence. 0 = single-shot recursive for the whole horizon (compounds error badly over a year — don't use for long backtests).
--known-pricesFeed the test period's actual prices as a known promo calendar (otherwise price is carried forward flat). This is an upper bound — in real production you'd only know planned/future prices.
--weather PATHAdd weather as a known exogenous signal.
--calibrateLeakage-free rolling bias correction (scales each refresh block by the actual/forecast ratio of already-realized blocks). Keep this on — it consistently helps.
--weights / --monotoneOpt-in volume sample-weighting / monotone price constraints. Both were tried and rejected — they regressed WAPE on this data. Off by default; don't turn them back on without new evidence.
--forecast-futureAlso refit on all data and forecast --horizon days beyond the end of history.

7. Current results & the open problem

Best config so far (the command above) gets daily WAPE (SKU-ZIP) down to ~0.49, monthly WAPE ~0.16, with volume error near 0%. But that near-zero net bias is misleading — it's a coincidental cancellation, not evenly-good forecasting:

SegmentWAPEBiasNotes
PEAK (busiest ~11% of rows)~0.49−45 to −48%carries ~26% of all units, badly under-forecast
NON-PEAK active~0.40–0.50+9 to +22%consistently over-forecast
ZERO-demand days—smalloccasional false-positive predictions

In plain terms: the model shaves peaks and pads troughs. This under-forecast gets worse at finer grain (day −12% → SKU −31% → SKU-ZIP −45%). We tried removing anomalies/spikes and rejected it — the "spikes" are real demand the model already under-predicts (71% of the worst-error rows are under-forecasts, not over-forecasts), so treating them as noise would make things worse, not better.

8. Where to contribute next

Prioritized list, highest-value first — these directly attack the peak-shaving gap above rather than chasing overall WAPE in a way that could hide it further:

Tier 1 — cheap, attacks the peak under-forecast directly

  1. Asymmetric / quantile loss (objective closer to the 0.6–0.65 quantile, so under-forecasting peaks is penalized harder than over-forecasting troughs)
  2. Raise tweedie_variance_power from 1.2 → 1.4–1.6 (fatter right tail)
  3. Shorter refresh cadence: --refresh-days 7

Tier 2 — attacks the trough over-forecast / zero-demand false positives

  1. Two-stage hurdle model: P(ships>0) × E[units | ships>0]
  2. Segment-specific models (global GBM for smooth/erratic series, hurdle/Croston for intermittent/lumpy ones)
  3. Hierarchical reconciliation (MinT / bottom-up) to borrow stability from aggregates for sparse series

Tier 3 — structural / needs more data

  1. Weekly-grain forecasting (matches the actual replenishment decision cadence)
  2. Stockout censoring (needs inventory data we don't currently have)
  3. Time-series CV hyperparameter tuning; LightGBM+XGBoost blend
  4. Real future promo/temperature plans in production (the backtest currently uses actuals via --known-prices/--weather, which is an upper bound on what you'd know in advance)
Before you start: re-run the best-config backtest first (see above) and confirm you reproduce ~0.49 WAPE and the peak-shaving pattern. That's your baseline to beat.

9. Gotchas & known issues

  • uv.lock is stale. Dependencies were installed with plain pip into .venv, not via uv, so the lock file doesn't reflect the current pyproject.toml. If you have uv installed, regenerate it with uv lock; otherwise just pip install from pyproject.toml as shown above.
  • No fixed random seed in lgb_params() (forecast.py) — re-runs should be close but aren't guaranteed bit-identical.
  • This repo is public. weather.tsv and backtest_2025.tsv are checked in (non-sensitive / derived), but the raw With_Price.tsv deliberately is not. Don't add it or anything else with real pricing/customer data to a commit.
  • Holiday cache is hardcoded to 2021–2027 (_HOLIDAY_CACHE in forecast.py) — forecasting dates beyond 2027 will silently get is_holiday=0 instead of erroring. Worth fixing if long-horizon forward forecasts become a priority.
  • Different "known" grades of realism: --known-prices and --weather feed the backtest actual future prices/weather, which is a fair way to isolate model quality but is optimistic vs. real production (see Tier 3, item 10 above).

10. Glossary

WAPEWeighted Absolute Percentage Error = Σ|actual−forecast| / Σactual. The project's primary accuracy metric; lower is better.
Bias(Σforecast−Σactual) / Σactual. Positive = over-forecasting on net, negative = under-forecasting. A bias near 0 does not mean the forecast is accurate everywhere — see Current results.
Tweedie lossA loss function for non-negative, zero-inflated targets (a mix of a point mass at 0 and a continuous positive distribution) — a natural fit for intermittent shipment counts.
Recursive forecastMulti-step forecasting where each predicted day is fed back in as if it were real, so it can seed the lag features of the following days.
Rolling-origin backtestInstead of one long recursive run over the whole test period (which compounds error), re-seed the model's lag features with real actuals every N days and forecast N days at a time — closer to how the model would actually be operated.
Croston / TSBClassic intermittent-demand forecasting method (estimates demand size and probability of a non-zero day separately) — used here as a baseline, not the main model.
Syntetos–Boylan classificationA standard way to categorize demand series (smooth / erratic / lumpy / intermittent) based on how often and how variably they sell.
ASINProduct identifier (Amazon Standard Identification Number convention, used here as a generic per-SKU key).
